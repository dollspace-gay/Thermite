# ORIGINAL AUDIT (verbatim — baseline `93d3cbc0`)

# Audit: Thermite (dollspace-gay/Thermite @ 93d3cbc0)

**Scope.** Static audit of the repository's code, Lean proofs, and trust-chain claims. I could not execute the toolchain in this sandbox (its network allowlist blocks the pinned Rust 1.95.0 and Lean 4.29.0 toolchain downloads, and Verus/Z3), so nothing here re-runs `make audit`; everything below comes from reading the sources, re-deriving checkable facts (e.g. the SHA drift tripwire) by hand, and cross-checking claims against implementation.

**Repo shape.** ~32k lines of Rust in `forge` plus six library crates, ~7,750 lines of Lean 4 (192+ theorems/lemmas, 13 "negative pin" modules), 17 conformance programs, ~930 Rust `#[test]`s, golden emitted-Verus files, a 524-line audit script, and an unusually large body of design documentation (`.design/`, RATIONALE.md). The entire history is 385 commits over 8 days (2026-06-04 → 06-11), single author — evidently an agent-driven build, which makes the verification discipline the main thing worth auditing.

---

## Verdict in one paragraph

The architecture is sound and — more unusual — the *claims about the architecture* are honest. The headline "universal faithfulness theorem" is exactly what its own header says it is: a composition theorem that takes the per-run Z3 attestation as an explicit hypothesis (`h_tv`), not a Lean proof of the production lowerer. The residual trust base (Lean kernel + 3 standard axioms, Z3/Verus, spec-equals-intent, the inspection-tier Rust↔Lean correspondence, rustc/LLVM) is enumerated in RATIONALE.md, in the Lean module headers, and printed by `scripts/audit.sh` itself. I found no `sorry`/`axiom`/`native_decide` in any Lean proof position (all matches are comments), no Verus escape hatch outside the declared `#[slag]`/`#[boundary]` seam, and several anti-cheat mechanisms (counterexample-never-degrades, timeout-never-fabricated-as-divergence, 0/0-mutants-fails) that are implemented, not just described. The findings below are real but second-order: a known-open lowering bug, an inherently fragile inspection-tier bridge, a CI gap on the Lean spine, and a few semantic corners of the Lean model worth pinning down.

---

## What the proofs actually establish (and don't)

The Lean spine proves **T1**: the *reference encoders* (Lean models `RefEncode.lean`, `Exec.lean`, `Exec/Stmt.lean`) are denotation-faithful to the source semantics `denote`, by structural induction, for the frozen subset. `Faithfulness.lean` then proves **T2**: *if* Z3 attests per run that the production lowering's output is equivalent to the reference encoder's output (`h_tv`, a structure field explicitly labeled "THE TRUST BOUNDARY — supplied by Z3, NOT proved in Lean"), *then* the lowering is faithful. Three things follow:

1. **The "∀ programs" claim is conditional on Z3 per run.** The repo says this everywhere it matters, including the audit script's residual-trust printout. Honest.
2. **The Lean encoders are hand-written models of the Rust encoders** (`thermite-tv/src/{ref_encode,exec_encode,exec_stmt_encode}.rs`). The bridge is an arm-by-arm inspection doc (`.design/verified/rust-lean-correspondence.md`) with pinned commit SHAs and a drift tripwire in `audit.sh` check [4]. I re-ran the tripwire by hand: **all six pins match current `git log -1` last-touch SHAs** (ref_encode 579d3d48, exec_encode 43c9a6c8, exec_stmt_encode 21b84c5f, combinators c0b1d8a3, lean_export 3373215e, lean spine 1438dc5f). I also spot-checked one slice myself: `binop_str`'s 18-arm operator map and `cast_target` in ref_encode.rs against `encOp/encLog/encArith/encCast` in RefEncode.lean — they agree arm-for-arm. The inspection tier remains the weakest deliberate link (see findings F2/F3), and the repo says so.
3. **Non-vacuity is engineered, not asserted.** The spine pairs every positive theorem with negative lemmas (e.g. `cast_paren_drop_breaks_soundness`, `match_arm_swap_breaks_soundness`) showing a deliberately wrong encoder *fails* the theorem at a concrete environment, plus 13 `Pin*.lean` modules that pin entire bug classes. This is the right defense against proving `True` impressively.

The Z3-demotion work (`SmtDemo.lean`, Lean-SMT/cvc5 kernel reconstruction) is correctly labeled a partial-scope proof of concept for the QF-linear fragment; RATIONALE lists the concrete upstream blockers rather than claiming the demotion.

## What `forge check` actually certifies

`check.rs` runs parse → validate → effect check → per-item: structural vacuity triage → solver vacuity (two Z3 queries) → lower → Verus (`--output-json`, structured summary parsing, not stdout grep) → mutation scoring → certificate. Anti-cheat properties I verified in code, not just comments:

- **Counterexample never degrades** (`degrade.rs::run_ladder` returns the hard-fail cert without invoking the L2/L1 closures; hermetic tests pin it).
- **Solver timeouts are never fabricated into findings** — one shared rlimit discriminator (`tv_signal.rs`) used by all three TV phases, created after the three private copies drifted (#192); a timeout routes to Timeout/Unverifiable, never Counterexample/Divergent.
- **`#[verifier::external_body]` is only emitted for `#[boundary]`/`#[slag]` items** (lower.rs:2471), i.e. exactly the declared trusted seam — and the decision function itself is Verus-proven in `thermite-verified`. So "Verus: 0 errors" can't be silently hollowed out by trusted bodies elsewhere.
- **Open typed holes refuse both check and build** (shared `open_hole_reason`).
- **Mutation gate**: 0/0 scoreable mutants is below-floor (gated WeakContract), never a vacuous 100%.

Important scoping fact: **translation validation is not part of `forge check`** — `tv`/`exec-tv`/`body-tv` are separate commands, run over the corpus by the deep audit. So a bare L3 certificate attests "Verus proved the *lowered* artifact against the *lowered* contract"; faithfulness of lowering to source meaning is established by the separate TV runs plus the theorem. RATIONALE's trust-chain account is consistent with this, but a casual reader of the README's certificate paragraph could think one `forge check` buys the whole chain (finding F5).

The seccomp cage is real: `sandbox.rs` emits a classic `sock_filter[]` BPF program (arch guard → load `nr` → `BPF_JEQ` per allowed syscall → `RET_ALLOW`, default `RET_KILL_PROCESS`) installed via `prctl(PR_SET_NO_NEW_PRIVS)` + `PR_SET_SECCOMP` as the first statements of the generated `main`, with a documented fx→syscall table whose `pure` baseline excludes `openat`/`socket`/`getrandom`/`clock_gettime`. The `unsafe` lives only in the emitted binary and in the editor's declared termios boundary — `grep` confirms no other unsafe in the workspace.

The audit script itself deserves credit: a SKIP of a guarantee-bearing check exits 3 ("INCONCLUSIVE"), distinct from pass (0) and fail (1), so automation can't read a Verus-less run as green. Its check [1] parses `#print axioms` for the five load-bearing theorems against the exact allowed set — the right check, implemented with the right parsing.

## Findings

**F1 — Known-open lowering bug, correctly pinned (low severity, fails closed).** `lower_inv_operand` (struct type-invariant path) lacks the #146 cast-`<` parenthesization fix that `lower_binary_operand` got, so `} inv (x as u32) < cap` lowers to a mis-parsing form. Pinned as an `#[ignore]`d divergence test (blocker #148). Failure mode is a Verus parse error → L0, never a false certificate. All 15 `#[ignore]`s in the tree follow this tracked-divergence convention; none hide a green-path failure.

**F2 — The Verus-meaning bridge is informal, and two semantic corners deserve pinning.** `tokRel/tokArith/tokCast` are *claimed* to be "the standard-model interpretation of the emitted Verus token," but that claim is itself inspection-tier. Two places to verify against actual Verus/SMT-LIB semantics: (a) `arithDenote`'s `div`/`rem` use Lean's `Int./`/`Int.%`, and the comment hedges "Euclidean-ish / T-division" — Verus `int` division is SMT-LIB Euclidean; if Lean's instance and Verus's semantics differ on negative operands the model diverges exactly where the divisor-≠0 convention doesn't help. The doc leans on source-side obligations, but the negative-operand case should get its own pin lemma or a written rule excluding it from the frozen subset. (b) `castDenote` treats `as u64/u32/usize` as value-preserving with the no-overflow frame "carried as a source obligation," while Verus `as` truncates; the #228 contract-tv entry shows narrowing cases are routed to honest *Unverifiable*, which is sound, but the obligation-carrying convention is spread across comments rather than stated once normatively. Suggest: add Pin lemmas for negative-div and out-of-range-cast, or a single normative section in thermite-semantics.md.

**F3 — Inspection-tier bridge is one `git commit --amend` away from staleness in spirit.** The drift tripwire compares last-touch SHAs, which catches edits but not the quality of a re-audit: nothing forces the *re-inspection* to be real when someone re-pins (the 2026-06-10/11 amendments re-pinned twice in two days). This is inherent to the tier and disclosed; the mechanized extraction bridge on the roadmap is the actual fix. Until then, treat correspondence re-pin commits as the highest-review-priority diffs in the repo.

**F4 — CI never builds the Lean spine.** `ci.yml` runs the full Rust gauntlet *with Verus installed* (good — the teeth suites run in CI), but `lake build` + the axiom probe run only in local `make audit`. A commit that breaks the Lean build, or the pinned Lean-SMT `rev = "main"` dependency drifting upstream (it is pinned to a *branch*, not a SHA — `lake-manifest.json` locks it, but a manifest update floats), would not be caught until someone runs the deep audit. Recommend a CI job (even weekly, cached) doing `lake build` + the check-[1] axiom probe, and pinning lean-smt to a commit in `lakefile.toml`.

**F5 — Two README phrasings outrun the mechanism.** (a) "dozens of deliberately-broken mutant copies … the contract must *catch* them" — the actual gate is a 60% kill-ratio floor (`MUTATION_FLOOR = 0.60`) with prover-proved-equivalent-mutant exclusion; RATIONALE explains the floor honestly, the README implies totality. (b) The certificate paragraph ("forge check turns that into a certificate: proven for all inputs, promise non-empty, mutants killed") is true of `check` alone, but the *faithfulness* leg of the trust chain needs the separate TV commands; one clause acknowledging that would align the README with the audit script's own accounting.

**F6 — Fragile heuristics, documented but worth hardening.** Timeout-vs-counterexample is discriminated by presence of a `--profile` Z3 instantiation report plus a phrase set ("rlimit exceeded", "resource limit exceeded", …) matched against solver output; a future Verus/Z3 wording change degrades gracefully (to the failure path, never to success — verified in code) but could misclassify timeouts as counterexamples, which contradicts the never-fabricate rule's spirit. The phrase-drift regression test helps; pinning Verus (done: 0.2026.05.24) is the real mitigation.

**F7 — Could not independently re-derive the dynamic claims.** Whether the editor's edit/nav core actually certifies L3, whether the golden `binary_search.verus.rs` verifies under third-party Verus, and whether the corpus shows zero divergences are all claims this audit could not execute. I can say: the golden Verus file is a legitimate, complete proof artifact (well-formed vstd/`verus!` syntax, a correct loop invariant — `forall_below(lo, <needle)` / `forall_from(hi, >needle)` with the assert-forall-by discharge at `lo == hi`), not a stub; the editor honestly splits a verified core (buffer/cursor/nav/render/decode with real `ens`/`dec`) from an L1 termios/syscall boundary and an L1 `fx diverge` event loop; and CI runs the verus-bearing tests on every push. Anyone with the pinned toolchains should run `make audit` to close this.

## Code-quality notes (minor)

The Rust is unusually disciplined: every module carries a requirements table mapping design REQ → shipped evidence → consumer; scratch-dir hygiene around solver invocations (Drop-guard `remove_dir_all` on every exit path, fixing a real ENOSPC); crate-name and output-parsing gotchas handled with grounded comments; determinism rules (pinned seed, sorted/deduped emissions, solver wall-time excluded from the certificate oracle). The comment style is extremely loud (caps, issue numbers everywhere) — high signal for auditors, though the comment-to-code ratio means doc-drift is the main long-term maintenance risk; the repo's own pin/tripwire conventions are aimed at exactly that.

## Recommendations, ordered

1. Fix #148 (`lower_inv_operand` cast-`<` paren) and un-ignore the pin.
2. Add Lean pin lemmas (or a normative semantics section) for Euclidean-vs-truncated division on negatives and out-of-range `as` narrowing (F2).
3. Add a CI job for `lake build` + the axiom probe; pin lean-smt to a SHA (F4).
4. Soften the two README phrasings (F5) — the repo's credibility rests on the claims never exceeding the mechanism, and everywhere else they don't.
5. Longer term: the mechanized Rust↔Lean extraction bridge (already on the roadmap) is the single highest-leverage trust upgrade.

# Part 2 — second pass (loop rule, anti-Goodhart machinery, exporter)

## The loop `while_rule` (Exec/Loop.lean)

Clean partial-correctness while-rule: entry (`I st₀`), preservation (one `blockThread` step keeps `I` under `I ∧ cond`), and a `h_run : loopDenote … = some stf` hypothesis carrying "the loop exits," concluding `I stf ∧ cond = false`. Termination is deliberately *not* a Lean premise — it stays the per-run Verus `decreases` residual, stated three times over (module header, loop-tv.md, RATIONALE). The fuel-indexed `loopDenote` is ∀-fuel, so fuel is an induction measure, not a cap on what's certified — the vacuity dodge is explicitly argued away. Core-Lean-only proof (`simp`/`omega`/`decide`, no Mathlib). One more inspection-tier joint to note: the invariant is modeled as a `State → Prop` predicate while the Rust side encodes it as a Verus boolean expression (`encode_inv_clauses`); the modeling choice carries a written justification, but it's another seam the future extraction bridge should mechanize.

## The anti-Goodhart machinery holds up under reading

**Solver vacuity (`vacuity_solver.rs`)** implements the two textbook queries correctly: tautology = lower the *real* item, splice its verbatim contract into a `proof fn taut_check(<params>, result: <RET>) requires R ensures E {}` with an **empty body and arbitrary `result`** — if Verus proves it, the `ens` is body-independent → reject; vacuous precondition = `proof fn vac_check(<params>) requires R { assert(false); }` — provable iff `R` is unsatisfiable → reject. Inverted-verdict logic (Verus success = bad news) is handled explicitly, and a timeout/VIR error is a `ForgeError`, never a silent clean.

**Mutation (`mutation.rs`)**: deterministic operator catalogue (constant perturbation, a frozen binop-flip table chosen so every flip is value-distinguishable, early-return injection, branch negation/swap with complementary comparison flips). The equivalent-mutant exclusion is the strong version: a survivor is excluded only if Verus *proves* it observably equivalent to the real body under `req`, and it drops from both numerator and denominator; an all-equivalent-no-kills fn reduces to 0/0, which fails the floor rather than passing vacuously.

**The overflow-vacuity escape is found and pinned** (`PinExecOverflowVacuity.lean`): a body that always overflows (`bodyDenote = none`) makes the partial-correctness contract obligation vacuously provable even for a false `ens`. The pin proves both halves — the vacuous discharge *and* that the conjoined per-item overflow obligation (`(bodyDenote …).isSome`) is refuted at the same state — so the conjunction rule blocks the certificate. This is exactly the class of subtle soundness hole that distinguishes a serious verification effort from theater; finding it pinned in the tree, with a concrete `2⁶⁴−1 + itself` witness, raised my confidence more than any positive theorem did.

## Findings added in this pass

**F8 — Req-conditioned TV vs unconditional `h_tv` (documentation gap, likely sound).** `equivalence_obligation` asserts `(P_production) <==> (P_reference)` inside a `proof fn` optionally carrying `requires <req>` — so for `ens` clauses, production and reference need only agree on req-satisfying inputs. `Faithfulness.lean`'s `FnTvWitness.h_tv_contract` is an *unconditional* equality at the witness env. These reconcile if the certificate's quantification is understood as ranging over req-satisfying environments (which is what an `ens`-under-`req` certificate means), but I did not find that bridging argument written down in one place. One paragraph in `thermite-semantics.md` (and a check that the `req` clause's own obligation is emitted *unconditioned*) would close it.

**F9 — The frozen subset is narrower than the README's register suggests.** The combinator cage is 8 combinators, monomorphic over `Seq<u32>`/`u32` (with separately-grounded `String`/`Vec`/`Map<u64,u64>` views); loops are single v1 `while`, no `break`/`continue`/nested loops/multi-exit returns; user ADTs are outside the proven match fragment (built-in `Option`/`Result` only). All disclosed in the coverage sections — but the README's "a programming language" framing will read to newcomers as more general than the current proven core. A scope table near the top of the README would prevent disappointment-driven distrust.

**F10 — `lean_export.rs` is the newest, largest, least-settled surface.** 2,967 lines, last-touched the day before the audit snapshot, three theorem tiers with a capture-unsafe-substitution refusal path (tested), and a hard gate refusing export when any reachable spec-fn lacks a registry definition. The refusal-over-silence discipline is right; but as the freshest code on a trust-bearing path (it feeds the Z3-demotion/Lean-engine-#2 arc), it has had the least soak time and the correspondence doc's own amendment history shows two re-pins in two days around it. Treat it as the area where the next bug most likely lives.

## Code hygiene (confirms Part 1)

The "no panics" claims are real: zero `unwrap`/`expect` in the non-test regions of the two largest forge modules (the 81 workspace hits are all inside `mod tests`); library crates use span-bearing `Result` error enums throughout; the only `panic!` in emitted output is the *intended* L1 contract-violation abort of the generated program. Two TODO-class markers in the entire tree. For an 8-day, 385-commit, agent-built codebase, this level of consistency is the most surprising empirical fact in the repo.

## Bottom line after both passes

No soundness-breaking defect found by inspection. The trust chain is correctly factored, the escape hatches are loud and enumerated, the anti-cheat layers are implemented rather than aspirational, and the one open lowering bug fails closed. The substantive risks are concentrated where the repo itself says they are: the hand-inspected Rust↔Lean bridge (F2/F3/F8), the un-CI'd Lean spine (F4), and the freshest exporter code (F10). The decisive remaining step for an outside skeptic is dynamic: run `make audit` with the pinned Verus and Lean toolchains — this environment couldn't, so the L3/zero-divergence/teeth-suite claims remain re-derivable but not re-derived here.

# Part 3 — re-cut against the prior review's open questions

Context recovered from the earlier conversation thread: this audit sits inside a specific dispute. The objection on the table (Maxine's) was that Thermite's soundness evidence was **existential** — golden files and per-program TV runs each show "∃ a program where the lowering was faithful" — while the claims read as universal, making Thermite "an unproved translation step over Verus." The agreed decomposition was three links: (1) Z3 soundness, (2) Verus VC-gen soundness — both inherited from audited systems, relative to their own consistency — and (3) **the Thermite→Verus lowering faithfulness, the link Thermite owns**, which at the time of that exchange was ∃-only with the ∀-proof open. The prior review session settled the S⊥R circularity question but could not read most of the Lean source through web tooling. This pass had the full tree on disk, so here is each open item closed or re-scoped.

**Q1 — Is S independent of R? (Confirmed: yes, and more thoroughly than before.)** The prior session's evidence was the token indirection in the `cmp` case (`denote` interprets `CmpOp.eq` directly as `x = y`; `refDenote` goes through `tokRel (encOp op)`, so `ref_sound` must prove a real round-trip per operator). With the whole tree readable, that pattern holds across every construct class: arithmetic (`tokArith ∘ encArith` vs direct `arithDenote`), casts (`tokCast ∘ encCast`, including the independently-modeled parenthesization that makes the #122/#146 cast-paren class a *provable* failure of an unfaithful encoder), byte-view dispatch (`byteView ∘ encByteAt/encLen`), and the combinators. Where the two recursions deliberately *share* a helper (`arithDenote`, `castDenote`, `seqIdx`), the module headers say so and explain why the sharing is not the soundness content for that construct (the encoder's *choice of token/dispatch/parenthesization* is). And the negative lemmas are the proof the independence is load-bearing: a swapped match arm, a dropped cast paren, a misdispatched byte-view each *disprove* soundness at a concrete environment. Verdict unchanged but now grounded in the full source rather than one case: not circular.

**Q2 — Is link 3 (lowering faithfulness) still ∃-only? (No — but say precisely what it became.)** The honest status today is: the **∀-statement now exists and is kernel-checked, as a conditional theorem.** `lowering_faithful` proves: for *every* program and *every* (arbitrary, universally-quantified) production-lowered meaning, *if* the per-run Z3 TV attests `⟦lower(P)⟧ = ⟦ref(P)⟧`, *then* `⟦lower(P)⟧ = ⟦P⟧_S`. The existential→universal conversion is real — the conclusion quantifies over all programs passing TV, not over the corpus — and the construction genuinely consumes the TV result (the `lowered` side is an arbitrary value, so `h_tv` is false unless Z3 in fact attested it; the theorem cannot manufacture faithfulness for a divergent lowering). What link 3 has been **reduced to**, rather than closed unconditionally, is: (a) Z3's soundness *per run* on the TV query — which is link 1 again, not a new trust item, with a partial kernel-replay demotion PoC shipped; and (b) the **Rust↔Lean encoder correspondence** — the claim that the Rust `ref_encode`/`exec_encode`/`exec_stmt_encode` that actually run implement the Lean-proven algorithm — held at the inspection tier (arm-by-arm audit doc, SHA-pinned, drift-tripwired; I re-ran the tripwire by hand and all six pins are current, and independently spot-checked the binop/cast arms). So the defensible claim is no longer "∃-only at the lowering link"; it is: *the lowering link is now a kernel-checked verified-validator theorem whose per-run premise Z3 discharges, with one named residual (CORR) at the inspection tier.* That is a categorical upgrade from where the dispute left it — and it is also not "link 3 is proven," full stop. Both halves of that sentence matter.

**Q3 — The toolchain self-proofs Doll cited check out.** The `thermite-verified` claims from the prior exchange exist in source: the effect-subsumption equivalence is exhaustively established over the full 2⁹ × 2⁹ = 262,144-pair u16 bitset domain, the degrade anti-cheat (counterexample never downgrades) is Verus-anchored with hermetic tests, and the seccomp allowlist soundness sits behind the proved `should_emit_external_body`/`io_allow` decisions. One honesty nuance worth knowing for the conversation: the landed mechanism is **(c) proved-reference + exhaustive equivalence test**, not (b) "the proved artifact is the linked production code" — the module says so explicitly. For these finite domains, exhaustive equivalence is as strong as linking; but if anyone claims "the proven code is the running code," the accurate version is "the running code is exhaustively equivalent to the proven code over its entire input domain."
